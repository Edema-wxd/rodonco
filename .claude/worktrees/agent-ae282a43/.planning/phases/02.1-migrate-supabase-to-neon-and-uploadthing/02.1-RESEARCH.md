## Summary

Phase 2.1 is a pure infrastructure swap with zero customer-facing changes. Three parallel subsystems are migrated: the database layer (Supabase Postgres → Neon + Drizzle ORM), authentication (Supabase Auth → NextAuth.js v5 with Credentials provider), and file storage (Supabase Storage → Uploadthing v7). All six original tables are re-declared in Drizzle schema-as-code, matching the existing column names from `supabase/migrations/0001_initial_schema.sql` exactly. The existing TypeScript interfaces in `src/types/index.ts` continue to work because column names are preserved.

The most significant research finding is a **CRITICAL discrepancy** in the CONTEXT.md decision D-16: it lists `NEXTAUTH_SECRET` (NextAuth v4 name) and `UPLOADTHING_SECRET` + `UPLOADTHING_APP_ID` (Uploadthing v6 names). The actual v5/v7 names are `AUTH_SECRET` and `UPLOADTHING_TOKEN` respectively. The planner must use the verified names, not the CONTEXT.md names, since CONTEXT.md was written before version-checking occurred.

The second significant finding: Uploadthing v7's `createRouteHandler` changed its return — it now returns a **single** handler function, not separate `{ GET, POST }` exports. The official docs still show `{ GET, POST }` in the current getting-started guide; the v7 migration notes document the change. Research shows the docs are slightly inconsistent; the safest pattern (confirmed in official docs) is the `{ GET, POST }` destructure shown in the getting-started guide.

**Primary recommendation:** Implement in wave order: (1) Drizzle schema + Neon wiring, (2) NextAuth v5 config + middleware, (3) Uploadthing v7 route, (4) env cleanup. Each wave is independently testable before the next.

### Pattern 2: drizzle.config.ts (project root)

**What:** Drizzle Kit configuration. Uses `DIRECT_DATABASE_URL` for migrations (not pooled) to avoid PgBouncer incompatibility with DDL statements.
**Why two URLs:** Neon's pooled URL routes through PgBouncer, which does not support schema migrations (DDL). `drizzle-kit push` must use the direct (non-pooled) connection string.

```typescript
// Source: neon.com/docs/guides/drizzle-migrations
import "dotenv/config";
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  schema: "./drizzle/schema.ts",
  out: "./drizzle/migrations",       // Not used for push, but good practice
  dialect: "postgresql",
  dbCredentials: {
    url: process.env.DIRECT_DATABASE_URL!, // Direct (non-pooled) for migrations
  },
});
```

[CITED: neon.com/docs/guides/drizzle-migrations — "use direct connection for schema migrations"]
[ASSUMED: DIRECT_DATABASE_URL as the env var name — Neon provides both URLs in dashboard; exact env var name is a convention, not mandated]

### Pattern 4: NextAuth v5 Configuration

**What:** Auth.js v5 with Credentials provider. Because no edge-incompatible adapter is used (JWT sessions, no DB session table), a single `auth.ts` file suffices — no need for the auth.config.ts split pattern.

```typescript
// auth.ts (project root)
// Source: authjs.dev/getting-started/authentication/credentials
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";
import { db } from "@/lib/db";
import { admins } from "@/../drizzle/schema";
import { eq } from "drizzle-orm";
import bcrypt from "bcryptjs";

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [
    Credentials({
      credentials: {
        email: { label: "Email", type: "email" },
        password: { label: "Password", type: "password" },
      },
      authorize: async (credentials) => {
        if (!credentials?.email || !credentials?.password) return null;
        const [admin] = await db
          .select()
          .from(admins)
          .where(eq(admins.email, credentials.email as string))
          .limit(1);
        if (!admin) return null;
        const valid = await bcrypt.compare(
          credentials.password as string,
          admin.password_hash
        );
        if (!valid) return null;
        return { id: admin.id, email: admin.email };
      },
    }),
  ],
  session: { strategy: "jwt" },
});
```

[CITED: authjs.dev/getting-started/authentication/credentials]

### Pattern 6: NextAuth Middleware (middleware.ts)

**What:** Protects all `/admin/*` routes. Uses `middleware.ts` (not `proxy.ts`) because this project uses Next.js 15, not 16. `proxy.ts` is a Next.js 16+ rename.

```typescript
// middleware.ts (project root)
// Source: authjs.dev/getting-started/session-management/protecting
import { auth } from "@/auth";

export default auth((req) => {
  if (!req.auth && req.nextUrl.pathname.startsWith("/admin")) {
    const loginUrl = new URL("/admin", req.nextUrl.origin);
    return Response.redirect(loginUrl);
  }
});

export const config = {
  matcher: ["/admin/:path*"],
};
```

[CITED: authjs.dev/getting-started/session-management/protecting]
[VERIFIED: Next.js 15 uses middleware.ts, not proxy.ts — proxy.ts is Next.js 16+]

**IMPORTANT — Login page URL:** The redirect target is `/admin` (root admin path), which will serve the login page in Phase 4. The middleware must NOT redirect `/admin` itself (no trailing `:path+`) to avoid an infinite redirect loop. The matcher `/admin/:path*` matches `/admin/orders`, `/admin/products`, etc., but not `/admin` itself.

### Pattern 9: Admin Seed Script

```typescript
// scripts/seed-admin.ts
import "dotenv/config";
import { drizzle } from "drizzle-orm/neon-http";
import { neon } from "@neondatabase/serverless";
import { admins } from "../drizzle/schema";
import bcrypt from "bcryptjs";

const sql = neon(process.env.DATABASE_URL!);
const db = drizzle({ client: sql });

async function seed() {
  const email = process.env.ADMIN_EMAIL;
  const password = process.env.ADMIN_PASSWORD;
  if (!email || !password) throw new Error("ADMIN_EMAIL and ADMIN_PASSWORD must be set");
  const password_hash = await bcrypt.hash(password, 12);
  await db.insert(admins).values({ email, password_hash }).onConflictDoNothing();
  console.log("Admin seeded:", email);
  process.exit(0);
}

seed();
```

### Anti-Patterns to Avoid

- **Importing `db` in Client Components:** The Drizzle `db` instance uses `DATABASE_URL` which is a server-only secret. Add `import "server-only"` at the top of `lib/db/index.ts` to get a build-time error if accidentally imported client-side.
- **Using pooled URL for migrations:** `drizzle-kit push` via a PgBouncer pooled URL fails silently or errors. Always use `DIRECT_DATABASE_URL` (the non-pooled Neon URL) in `drizzle.config.ts`.
- **Using `NEXTAUTH_SECRET` instead of `AUTH_SECRET`:** NextAuth v5 requires `AUTH_SECRET`. The v4 name `NEXTAUTH_SECRET` is silently ignored.
- **Using `UPLOADTHING_SECRET` instead of `UPLOADTHING_TOKEN`:** v7 silently ignores the v6 env vars; uploads will fail with cryptic errors.
- **Middleware matching `/admin` itself:** The `/admin/:path*` pattern is correct — it protects sub-routes but NOT `/admin` (the login page). Using `/admin/:path+` would also protect `/admin` itself, causing an infinite redirect loop.
- **Not awaiting `auth()` in Uploadthing middleware:** `auth()` from NextAuth v5 is async. Calling without `await` returns a Promise, not the session.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

| Credential validation in middleware | Custom token parsing | `auth()` from NextAuth | Handles JWT verification, expiry, rotation |

## Common Pitfalls

### Pitfall 1: Pooled URL Used for drizzle-kit push

**What goes wrong:** `drizzle-kit push` hangs or fails with PgBouncer errors when the pooled Neon URL is used in `drizzle.config.ts`.
**Why it happens:** PgBouncer (Neon's connection pooler) does not support DDL statements or prepared statements in the way Drizzle Kit needs for schema introspection.
**How to avoid:** Add `DIRECT_DATABASE_URL` (the non-pooled Neon URL, no `-pooler` in hostname) to `.env.local` and use it exclusively in `drizzle.config.ts`. Use the pooled `DATABASE_URL` in `lib/db/index.ts` for runtime queries.
**Warning signs:** `drizzle-kit push` hangs indefinitely or throws "prepared statement already exists."

[CITED: neon.com/docs/guides/drizzle-migrations — "use direct connection for schema migrations"]

### Pitfall 2: AUTH_SECRET Not Set

**What goes wrong:** NextAuth v5 throws at startup: "MissingSecret" or signs tokens with an empty secret, making them invalid across restarts.
**Why it happens:** `AUTH_SECRET` is the only truly mandatory NextAuth v5 env var. Without it, the app crashes in production.
**How to avoid:** Generate with `npx auth secret` (writes to `.env.local` automatically). Add to `.env.local.example` and `src/types/env.d.ts`.
**Warning signs:** "MissingSecret" error in server logs; users logged out on every restart.

[CITED: authjs.dev/getting-started/installation]

### Pitfall 3: db Imported in Client Component

**What goes wrong:** Drizzle `db` instance imported in a client-side file causes Next.js build error or runtime failure — `DATABASE_URL` is not available in the browser bundle.
**Why it happens:** Developers mistake `lib/db/index.ts` for a shared module.
**How to avoid:** Add `import "server-only"` as the first line of `lib/db/index.ts`. This causes a build-time error if the file is ever imported from a client-side context.
**Warning signs:** Build error "server-only module imported from client component."

[CITED: Next.js docs — server-only package]

### Pitfall 4: Middleware Redirect Loop

**What goes wrong:** Visiting `/admin` (login page) redirects back to `/admin` infinitely.
**Why it happens:** Middleware matcher pattern `/admin/:path+` (plus, not star) matches `/admin` itself. The login page is protected, so unauthenticated users are redirected to... the protected login page.
**How to avoid:** Use `/admin/:path*` (star matches zero or more segments) or exclude `/admin` explicitly. The matcher `["/admin/:path*"]` matches `/admin/orders` but NOT `/admin`.
**Warning signs:** Browser shows "Too many redirects" on the `/admin` login page.

[ASSUMED: standard Next.js route matcher behavior; confirmed by NextAuth docs examples]

### Pitfall 5: auth() Called Without Await in Uploadthing Middleware

**What goes wrong:** Upload middleware always throws "Unauthorized" even for authenticated admins.
**Why it happens:** NextAuth v5's `auth()` is an async function. Without `await`, it returns a Promise (truthy), but `session.user` is inaccessible.
**How to avoid:** Always `const session = await auth()` in the `.middleware()` callback.
**Warning signs:** All uploads rejected with 401 even when admin is logged in.

[VERIFIED: authjs.dev — auth() is async function]

### Pitfall 6: Uploadthing v6 Env Vars

**What goes wrong:** Uploadthing silently fails or throws "Invalid token" errors.
**Why it happens:** v7 replaced `UPLOADTHING_SECRET` + `UPLOADTHING_APP_ID` with a single `UPLOADTHING_TOKEN` (base64 JSON). The v6 vars are not recognized by v7.
**How to avoid:** Get `UPLOADTHING_TOKEN` from the Uploadthing Dashboard > API Keys > V7 tab.
**Warning signs:** Uploads 401 with "Invalid token" or "Missing token."

[VERIFIED: docs.uploadthing.com/v7]

## Open Questions

1. **Where does Neon provide the direct vs pooled URLs?**
   - What we know: Neon's dashboard provides both. Pooled URL hostname contains `-pooler` (e.g., `ep-cool-darkness-123456-pooler.us-east-2.aws.neon.tech`). Direct URL has no `-pooler`.
   - What's unclear: The exact dashboard navigation path to find both — developer must check their Neon project dashboard.
   - Recommendation: Add a comment in `.env.local.example` explaining which URL to use where.

2. **Should `ordering_config` be re-seeded as part of this phase?**
   - What we know: The Neon DB starts empty; `drizzle-kit push` creates tables but does not seed data.
   - What's unclear: CONTEXT.md does not explicitly mention re-seeding `ordering_config` row 1 in Neon.
   - Recommendation: Include a seed step for `ordering_config` (id=1, `is_ordering_open=true`, `next_delivery_date` = next Saturday) as part of this phase, OR document it as a dependency for Phase 3.

3. **Does `auth()` work inside Uploadthing's middleware callback without a Request?**
   - What we know: NextAuth v5's `auth()` can be called as a route handler wrapper or standalone — but the standalone call requires that the request context is available via Next.js's async request headers.
   - What's unclear: Whether Uploadthing's middleware callback preserves Next.js's async request context.
   - Recommendation: Implement as `await auth()` and test; if it returns null unexpectedly, switch to `auth(req)` passing the middleware's `req` parameter.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | Yes | NextAuth v5 Credentials provider, bcryptjs (cost 12) |
| V3 Session Management | Yes | NextAuth JWT sessions; `AUTH_SECRET` for signing |
| V4 Access Control | Yes | middleware.ts guards `/admin/*`; Route Handler layer only DB access |
| V5 Input Validation | Yes | Credentials `authorize` — validate email/password presence before DB query |
| V6 Cryptography | Yes | bcryptjs (never hand-roll); `AUTH_SECRET` min 32 bytes |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Weak admin password hashing | Tampering | `bcryptjs` with cost factor 12 (not MD5, not SHA1) |
| Admin credential brute-force | Elevation of privilege | NextAuth has no built-in rate limiting — acceptable for MVP (single admin, not exposed to public) |
| `DATABASE_URL` leakage | Information disclosure | Never prefix `NEXT_PUBLIC_`; `import "server-only"` in lib/db/index.ts |
| JWT tampering | Tampering | `AUTH_SECRET` must be strong (32+ bytes random); generated via `npx auth secret` |
| Unauthenticated file upload | Elevation of privilege | Uploadthing middleware calls `await auth()` and throws `UploadThingError("Unauthorized")` if no session |
