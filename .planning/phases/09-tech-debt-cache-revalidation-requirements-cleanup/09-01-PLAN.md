<objective>
Replace passive TTL-based ISR caching with active tag-based invalidation across the shop's ordering config and product surfaces. Customer-facing shop pages currently lag behind admin mutations by up to 60 seconds (product CRUD) or 15 seconds (ordering toggle) because they rely on `export const revalidate = 60` and `unstable_cache(..., { revalidate: 15 })`. After this plan, admin mutations call `revalidateTag` and the customer surface updates immediately on the next request.

Purpose: Close the stale-cache bug. Per D-01/D-02, introduce exactly two tags — `"ordering-config"` and `"shop-products"` — and wire admin mutations to invalidate them. Per D-03, only config and product mutations trigger revalidation (order status changes do not affect the shop).

Output: Updated lib functions with tagged caches, admin route handlers calling `revalidateTag`, and customer pages with `revalidate` exports removed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin client → admin Route Handler | Authenticated admin posting/patching/deleting via fetch — request body may be malicious or oversized |
| Admin Route Handler → Drizzle / Postgres | Server-trusted DB writes; the new `revalidateTag` calls live on this side |
| Customer browser → cached page render | Untrusted reader; only sees fully-rendered HTML, never touches the cache or tags directly |
| `revalidateTag` call → Next.js cache subsystem | In-process; only callable from server code (Route Handlers / Server Actions) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Spoofing | Admin mutation routes | mitigate | Existing `auth()` session check at top of every handler is unchanged — no new auth surface introduced |
| T-09-02 | Tampering | `revalidateTag` argument | mitigate | Tag strings are hard-coded literals (`"ordering-config"`, `"shop-products"`), never derived from request input — no injection vector |
| T-09-03 | Repudiation | Admin mutations | accept | Existing `logActivity()` call records who did what; this plan does not alter the audit log path |
| T-09-04 | Information Disclosure | Cached shop data | accept | Cache stores public product/config data only — no PII, no auth tokens, identical to what was previously served via ISR |
| T-09-05 | Denial of Service | `revalidateTag` flood | accept | Only authenticated admins can trigger revalidation; revalidation is cheap (marks tag stale, next fetch repopulates). No new public-facing endpoint added |
| T-09-06 | Elevation of Privilege | New imports | mitigate | `revalidateTag` is server-only by Next.js design; importing it does not grant new privileges. No client code in this plan imports from `"next/cache"` |
| T-09-07 | Tampering | Stale-cache attack on closed ordering window | mitigate | After D-04 change, ordering toggle invalidates immediately rather than waiting 15s — closes the prior race window where a customer could submit an order during the 15s stale period after admin closed the window |
| T-09-SC | Tampering | npm/pip/cargo installs | N/A | No package installs in this plan — only `next/cache` (already a project dependency via `next`) is imported. Package legitimacy gate not triggered |
</threat_model>
