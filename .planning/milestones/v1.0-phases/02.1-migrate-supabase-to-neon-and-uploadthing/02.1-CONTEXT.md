# Phase 2.1: Migrate Supabase to Neon and Uploadthing - Context

**Gathered:** 2026-04-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Swap the infrastructure layer before Phase 3 builds on it. Specifically:
- Database: Supabase PostgreSQL → Neon serverless Postgres (with Drizzle ORM)
- Authentication: Supabase Auth → NextAuth.js v5 (Credentials provider, admin-only)
- Media storage: Supabase Storage → Uploadthing

The app-level Supabase clients (`lib/supabase/admin.ts`, `lib/supabase/client.ts`, `lib/supabase/server.ts`) are removed and replaced. All downstream phases (3–6) build on Neon + Drizzle + NextAuth. No customer-facing features change — this is pure infrastructure.

</domain>

<decisions>
## Implementation Decisions

### ORM / Query strategy
- **D-01:** Use **Drizzle ORM** with `@neondatabase/serverless` as the Postgres driver. All DB queries across Phases 3–6 use Drizzle's type-safe query API.
- **D-02:** Schema managed as **Drizzle schema-as-code** (`drizzle/schema.ts`). No migration files for MVP — apply with `drizzle-kit push` directly to Neon. Switch to `drizzle-kit generate` + migration files later when production data exists and schema changes need versioning.
- **D-03:** Remove `supabase/migrations/` folder (or keep for reference only). The Drizzle schema is the new single source of truth. All 6 existing tables must be re-declared in `drizzle/schema.ts` with equivalent column definitions.
- **D-04:** The three Supabase client files (`lib/supabase/admin.ts`, `lib/supabase/client.ts`, `lib/supabase/server.ts`) are deleted. Replace with a single `lib/db/index.ts` that exports the Drizzle `db` instance (server-only, uses `DATABASE_URL`).

### Authentication — NextAuth.js v5
- **D-05:** Use **NextAuth.js v5** (beta, a.k.a. Auth.js) with the **Credentials provider** for admin email/password login. No Supabase Auth dependency.
- **D-06:** Admin credentials stored in a **Neon DB `admins` table** (Drizzle schema): `id (uuid)`, `email (text, unique)`, `password_hash (text)`, `created_at (timestamp)`. Password hashed with `bcryptjs`.
- **D-07:** NextAuth session strategy: **JWT** (stateless, no DB session table needed for MVP).
- **D-08:** Route protection for `/admin/*`: NextAuth middleware in `middleware.ts` — redirects unauthenticated requests to `/admin` login page. Replaces the Supabase-based auth guard that Phase 4 was going to wire in `app/admin/layout.tsx`.
- **D-09:** Seed the `admins` table with an initial admin account. Credentials passed via env vars at seed time (not hardcoded).

### Uploadthing
- **D-10:** Install `uploadthing` and `@uploadthing/react`. Create the full upload infrastructure now so Phase 4 only needs to drop in the `<UploadButton>` component.
- **D-11:** Upload route handler at `app/api/uploadthing/route.ts`. File router defined in `app/api/uploadthing/core.ts` with a `productImage` route: `image`, max `4MB`, max 1 file. Upload middleware checks that the request is from an authenticated admin (NextAuth session).
- **D-12:** Returned upload URL stored in `products.image_url` (existing column) — no schema change needed.

### RLS / Access control
- **D-13:** **Drop RLS entirely on Neon.** All DB access goes through server-side Route Handlers and Server Components using a single `DATABASE_URL` connection string. The Route Handler layer is the security boundary — customers never touch the DB directly. No `anon` role, no per-table policies.
- **D-14:** `DATABASE_URL` is a server-only env var (never `NEXT_PUBLIC_`). The Drizzle `db` instance must only be imported in server-side files (Server Components, Route Handlers, server actions).

### Environment variables
- **D-15:** Remove: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`
- **D-16:** Add: `DATABASE_URL` (Neon connection string — pooled URL for serverless), `NEXTAUTH_SECRET` (random 32-byte secret), `NEXTAUTH_URL` (canonical app URL), `UPLOADTHING_SECRET`, `UPLOADTHING_APP_ID`
- **D-17:** Update `src/types/env.d.ts` and `.env.local.example` to reflect removed/added vars.

### Claude's Discretion
- Exact Drizzle column type choices (e.g., `timestamp` vs `timestamptz` — use `timestamp('col', { withTimezone: true })` for consistency with existing schema)
- Drizzle config file location (`drizzle.config.ts` at project root)
- Whether to use Neon's pooled vs direct connection URL (use pooled for serverless/edge; direct for migrations)
- Exact `admins` table seed mechanism (npm script, seed file, or manual Drizzle Studio)

</decisions>

<specifics>
## Specific Ideas

- Use Neon's **pooled connection URL** (`DATABASE_URL`) for all serverless/edge runtime queries. Neon provides a separate "direct" connection URL for migrations — use that in `drizzle.config.ts` as `DIRECT_DATABASE_URL`. Document both in `.env.local.example`.
- NextAuth v5 uses `AUTH_SECRET` as the env var name (not `NEXTAUTH_SECRET` from v4). Check the v5 docs — the var name changed. Update env.d.ts accordingly.
- The `admins` table is a new addition to the Drizzle schema — not in the original Supabase migration. It gets created by `drizzle-kit push` along with the other 6 tables.
- Uploadthing middleware in `core.ts` should call `auth()` from NextAuth to verify the uploader is an authenticated admin before accepting the file.

</specifics>
